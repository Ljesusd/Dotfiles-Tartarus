# Checkpoint — TartarusShell: Barra + Launcher fusionado

## Estado general

Este checkpoint registra el estado actual de la integración entre la barra superior y el launcher de TartarusShell.

La arquitectura dejó de usar una barra de búsqueda falsa dentro de `Bar.qml` y un `SearchBar` separado dentro de `Launcher.qml`.

Ahora:

- `LauncherSearch.qml` es el **único input real** del launcher.
- `Launcher.qml` contiene principalmente el panel de resultados.
- `LauncherState.qml` funciona como puente entre ambos.
- El launcher se abre con `SUPER + R`.
- `SUPER + R` coloca el foco directamente en el `TextInput`.
- El popup de resultados se ancla físicamente al `LauncherSearch`.
- El launcher siempre aparece en la pantalla donde vive la barra.
- Click fuera del launcher lo cierra.
- Click en cualquier otro componente o zona vacía de la barra también lo cierra.
- La escala visual de la barra se centralizó en `Style.qml`.

## Responsabilidades

### `LauncherSearch.qml`

Responsable de:

- mostrar el campo de búsqueda;
- contener el `TextInput`;
- recibir teclado;
- actualizar `LauncherState.query`;
- emitir navegación mediante `LauncherState`;
- pedir apertura al escribir o hacer click;
- registrar su `Item` como anchor del popup.

No sabe qué lista está activa.

### `LauncherState.qml`

Es la capa compartida de estado y señales.

Contiene conceptualmente:

```qml
property bool opened: false
property string query: ""

property var anchorItem: null
property var barWindow: null
```

Señales:

```qml
signal moveUpRequested()
signal moveDownRequested()
signal acceptRequested()
signal escapeRequested()
signal focusRequested()
```

Funciones principales:

```qml
open()
close()
toggle()
focusSearch()
```

`close()` también limpia el query.

### `Launcher.qml`

Responsable de:

- interpretar el query;
- seleccionar modo;
- mostrar resultados;
- navegar entre resultados;
- aceptar el resultado actual;
- administrar Applications / Actions / Schemes;
- animar el panel;
- cerrar mediante outside-click.

Modos:

```text
query normal
→ applications

>
→ actions

>scheme
→ schemes
```

# 5. Foco de teclado en Hyprland / Wayland

Hubo un problema importante:

- `forceActiveFocus()` podía enfocar el `TextInput` dentro de Qt;
- pero la barra no necesariamente recibía keyboard focus desde Wayland;
- por eso el cursor aparecía, pero el teclado no respondía.

Se probó `WlrLayershell.keyboardFocus: Exclusive`, que solucionó inicialmente el foco.

Posteriormente, al introducir `HyprlandFocusGrab`, tener ambos mecanismos simultáneamente causó conflictos.

La solución estable actual es mantener la barra con:

```qml
focusable: true
```

y dejar que el `PanelWindow` pueda recibir foco mediante su comportamiento normal de layer-shell.

El flujo actual es:

```text
SUPER + R
↓
LauncherState.open()
↓
opened = true
↓
HyprlandFocusGrab se activa
↓
focusRequested()
↓
LauncherSearch.TextInput.forceActiveFocus()
↓
teclado funciona
```

Importante:

No volver a combinar sin necesidad:

```text
WlrKeyboardFocus.Exclusive
+
HyprlandFocusGrab
```

porque ese fue el punto donde el launcher dejó de abrir/escribir correctamente.

# 6. Popup anclado a la Search

`Launcher.qml` dejó de usar un `PanelWindow` posicionado manualmente con valores como:

```text
y: 35
y: 40
```

Ahora usa un `PopupWindow` anclado directamente al `LauncherSearch`.

`LauncherSearch.qml` registra:

```qml
Component.onCompleted: {
    root.launcherState.anchorItem = root
}
```

Y el popup usa conceptualmente:

```qml
anchor.item: root.launcherState.anchorItem
```

Esto resolvió dos problemas:

1. Eliminó el hueco causado por geometría manual.
2. El launcher ya no aparece en el monitor activo equivocado.

# 7. Comportamiento multimonitor

Antes:

```text
SUPER + R desde monitor sin barra
→ launcher podía aparecer en ese monitor
```

Ahora:

```text
LauncherSearch vive en monitor A
↓
LauncherState.anchorItem = LauncherSearch
↓
PopupWindow se ancla a ese Item
↓
launcher aparece en monitor A
```

Aunque `SUPER + R` se pulse desde otra pantalla.

La arquitectura actual asume que el launcher pertenece a la barra existente.

Si en el futuro existe una barra por monitor, habrá que evolucionar la selección del anchor para escoger el `LauncherSearch` correspondiente.

# 11. Outside-click global

Se implementó `HyprlandFocusGrab` para detectar interacción fuera del launcher.

Ventanas que forman parte del grab:

```text
Bar window
Launcher PopupWindow
```

La lógica usa además un armado retrasado para evitar que el launcher se cierre inmediatamente durante la transición inicial de foco.

Conceptualmente:

```qml
property bool outsideClickArmed: false
```

y un `Timer` que habilita el cierre después de abrir.

Flujo:

```text
SUPER + R
↓
launcher abre
↓
outsideClickArmed = false
↓
pequeño delay
↓
outsideClickArmed = true
```

Después:

```text
click escritorio
click otra aplicación
click otra pantalla
↓
HyprlandFocusGrab cleared
↓
LauncherState.close()
```

Esto está probado y funciona como esperado.

# 12. Cierre al hacer click en la barra

`HyprlandFocusGrab` trabaja por ventanas completas.

Como `LauncherSearch` y los demás componentes viven dentro del mismo `PanelWindow`, el focus grab no puede distinguir:

```text
LauncherSearch
vs
Audio
vs
Network
vs
Clock
```

Por eso se añadió una segunda capa.

Los componentes de la barra reciben `launcherState`.

Antes de realizar su acción normal usan conceptualmente:

```qml
if (root.launcherState && root.launcherState.opened)
    root.launcherState.close()
```

Aplicado a:

- Workspaces
- Audio
- Network
- SystemTray
- Clock

Resultado:

```text
click LauncherSearch
→ NO cerrar

click Workspaces
→ cerrar + cambiar workspace

click Audio
→ cerrar + acción audio

click Network
→ cerrar + NetworkPopup

click SystemTray
→ cerrar + acción del tray

click Clock
→ cerrar
```

---

# 13. Cierre en zonas vacías de la barra

También se implementó cierre al clicar en zonas vacías del `PanelWindow`.

La estrategia usa un área de interacción de fondo en `Bar.qml`.

Conceptualmente:

```qml
MouseArea {
    anchors.fill: parent

    onClicked: {
        if (root.launcherState.opened)
            root.launcherState.close()
    }
}
```

Los controles interactivos están por encima y conservan sus propios handlers.

Resultado final:

```text
LauncherSearch
→ mantener abierto

Results popup
→ mantener abierto

cualquier otro control de Bar
→ cerrar

zona vacía de Bar
→ cerrar

escritorio
→ cerrar

otra ventana
→ cerrar

otra pantalla
→ cerrar
```

Este comportamiento ya fue probado y funciona.

# 22. Principio arquitectónico actual

```text
LauncherSearch
→ captura intención del usuario

LauncherState
→ comparte estado y eventos

Launcher.qml
→ interpreta intención y muestra resultados

Services
→ proporcionan datos y acciones
```

Esto evita que:

- la barra conozca internamente `appList`;
- el launcher conozca directamente el `TextInput`;
- los servicios dependan de la UI.

La separación actual permite seguir ampliando el launcher sin volver a convertirlo en un componente monolítico.
