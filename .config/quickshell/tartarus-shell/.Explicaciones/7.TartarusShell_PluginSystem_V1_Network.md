# Checkpoint — TartarusShell Plugin System V1 + Network

## Estado general

Este checkpoint registra el estado actual del sistema modular de plugins de TartarusShell y la migración completa de Network como primer plugin real.

La meta arquitectónica alcanzada es:

```text
Quickshell runtime
      ↓
PluginDiscovery
      ↓
manifest.json
      ↓
Plugin.qml
      ↓
PluginRegistry
      ↓
capabilities
   ├── bar-widget
   ├── panel
   └── service
```

Network ya no es una dependencia estructural de `shell.qml` ni de `Bar.qml`.

Si el plugin Network existe en `plugins/`, se descubre y se monta automáticamente.

Si el plugin Network no existe, el shell sigue cargando normalmente sin Network.

# 2. Filosofía arquitectónica

TartarusShell adopta una combinación de:

```text
Arquitectura modular/plugin-driven
→ inspiración tipo Omarchy

Integración visual/coherencia de superficies
→ inspiración tipo Caelestia
```

Los plugins siguen ejecutándose dentro del mismo runtime de Quickshell/QML.

No son procesos externos por definición.

# 3. Contrato Plugin V1

Un plugin completo sigue conceptualmente esta estructura:

```text
plugin/
├── manifest.json
├── qmldir
├── Plugin.qml
├── Service.qml
├── BarWidget.qml   opcional
└── Panel.qml       opcional
```

No todos los plugins tienen que implementar todas las capabilities.

Ejemplos futuros:

```text
Network
├── service
├── bar-widget
└── panel

Audio
├── service
├── bar-widget
└── quizá panel / osd

Notifications
├── service
├── overlay
└── panel
```

# 4. `manifest.json`

Network declara metadata y capabilities.

Conceptualmente:

```json
{
    "id": "network",
    "name": "Network",
    "version": 1,

    "capabilities": [
        "bar-widget",
        "panel",
        "service"
    ],

    "entryPoints": {
        "plugin": "Plugin.qml",
        "barWidget": "BarWidget.qml",
        "panel": "Panel.qml",
        "service": "Service.qml"
    }
}
```

Responsabilidades del manifest:

```text
id
→ identificador técnico

name
→ nombre humano

version
→ versión del contrato/configuración

capabilities
→ qué superficies/capacidades aporta

entryPoints
→ archivos QML correspondientes
```

---

# 5. `Plugin.qml`

`Plugin.qml` representa la instancia runtime viva del plugin.

Network expone conceptualmente:

```qml
readonly property string pluginId: "network"

readonly property var capabilities: [
    "bar-widget",
    "panel",
    "service"
]

readonly property Service service: Service {}
```

También expone fábricas declarativas:

```qml
readonly property Component barWidgetComponent: Component {
    BarWidget {
        plugin: root
    }
}

readonly property Component panelComponent: Component {
    Panel {
        plugin: root
    }
}
```

Estado UI del panel:

```qml
property bool panelOpened: false
property var panelAnchor: null
```

Funciones:

```qml
openPanel(anchor)
closePanel()
togglePanel(anchor)
```

---

# 6. Separación `Plugin.qml` vs `Service.qml`

La separación conceptual actual es:

```text
Plugin.qml
→ lifecycle/UI del plugin
→ panelOpened
→ panelAnchor
→ factories de UI

Service.qml
→ estado funcional real
→ datos
→ backend
→ acciones
```

Ejemplo:

```text
SSID
strength
networks
scan()
connect()
disconnect()
```

pertenecen a:

```text
Service.qml
```

Mientras:

```text
panel abierto/cerrado
anchor del panel
```

pertenecen a:

```text
Plugin.qml
```

---

# 7. `Service.qml`

Network Service quedó como fuente única de verdad para networking.

Responsabilidades conceptuales:

```text
connected
wifiEnabled
ssid
strength
networks
scanning

scan()
connectNetwork(...)
disconnect()
```

La UI no obtiene ni parsea información de red por su cuenta.

Flujo:

```text
backend / NetworkManager / procesos
              ↓
          Service.qml
           /       \
          ↓         ↓
   BarWidget.qml  Panel.qml
```

BarWidget y Panel comparten la misma instancia de Service.

---

# 8. `BarWidget.qml`

La representación compacta de Network ya vive en:

```text
plugins/network/BarWidget.qml
```

Responsabilidades:

```text
icono
SSID / strength
hover
click
interacción compacta
```

Consume:

```qml
plugin.service
```

No contiene backend de networking que pueda vivir en `Service.qml`.

Además expone la señal común:

```qml
signal interacted()
```

Esto permite que `Bar.qml` gestione lógica global como cerrar el launcher sin que Network conozca `LauncherState`.

Flujo:

```text
click Network
↓
BarWidget.interacted()
↓
Bar.qml
↓
closeLauncherIfOpen()
```

Después Network puede ejecutar:

```text
plugin.togglePanel(...)
```

sin acoplarse al launcher.

---

# 9. `Panel.qml`

El panel interactivo de Network vive en:

```text
plugins/network/Panel.qml
```

Consume:

```qml
plugin.service
```

y se controla mediante:

```qml
plugin.panelOpened
plugin.panelAnchor
```

Conceptualmente:

```qml
visible:
    plugin.panelOpened
    && plugin.panelAnchor !== null

anchor.item:
    plugin.panelAnchor
```

El panel puede mostrar:

```text
red actual
SSID
strength
lista de redes
scan
connect/disconnect
empty states
scanning state
```

pero no implementa el backend.

---

# 10. `qmldir`

Se añadió:

```text
plugins/network/qmldir
```

para que un `Plugin.qml` cargado dinámicamente pueda resolver correctamente los tipos locales:

```text
Plugin
Service
BarWidget
Panel
```

Además `Plugin.qml` usa:

```qml
import "."
```

para resolver el módulo/directorio local.

Este detalle forma parte del patrón actual de plugin.

---

# 11. `PluginRegistry.qml`

El registry mantiene plugins runtime registrados.

Conceptualmente:

```qml
property var plugins: []
```

Funciones principales:

```qml
registerPlugin(plugin)
plugin(id)
pluginsWithCapability(capability)
```

### `registerPlugin(plugin)`

Responsabilidad:

```text
validar referencia
evitar ids duplicados
añadir plugin
```

### `plugin(id)`

Permite lookup directo por id.

Actualmente Bar ya no necesita usar:

```qml
plugin("network")
```

para montar Network.

### `pluginsWithCapability(capability)`

Permite arquitectura genérica:

```qml
pluginsWithCapability("bar-widget")
pluginsWithCapability("panel")
```

El shell trabaja con capabilities, no con ids concretos.

```text
↓

```

`Bar.qml` ya no contiene referencias específicas a:


La barra solo conoce el concepto:

```text
bar-widget
```

# 13. Montaje genérico de bar widgets

Conceptualmente:

```qml
readonly property var barPlugins:
    pluginRegistry.pluginsWithCapability(
        "bar-widget"
    )
```

Luego:

```text
Repeater
→ un delegate por plugin

Loader
→ carga plugin.barWidgetComponent
```

Actualmente:

```text
barPlugins
└── Network
```

Futuro:

```text
barPlugins
├── Network
├── Audio
├── Bluetooth
└── Weather
```

sin modificar `Bar.qml`.

# 14. PanelHost genérico

`shell.qml` monta los paneles dinámicamente por capability.

Conceptualmente:

```qml
readonly property var panelPlugins:
    pluginRegistry.pluginsWithCapability(
        "panel"
    )
```

Host:

```text
PanelHost
└── Repeater
    └── Loader
        └── plugin.panelComponent
```

El shell ya no instancia:

```text
NetworkPanel

```

de forma explícita.

Solo conoce:

```text
panel capability
```

# 15. `PluginDiscovery.qml`

Se creó:

```text
core/PluginDiscovery.qml
```

Es responsable del descubrimiento automático de plugins dentro de:

```text
plugins/
```

Flujo:

```text
plugins/*
↓
FolderListModel
↓
cada carpeta candidata
↓
manifest.json
↓
validación
↓
entryPoints.plugin
↓
Loader
↓
Plugin.qml
↓
registerPlugin()
```

# 17. Validación del manifest

Antes de cargar código QML, `PluginDiscovery` valida como mínimo:

```text
id
capabilities
entryPoints.plugin
```

Esto evita intentar cargar plugins claramente inválidos.

Ejemplos de errores que deben detectarse temprano:

```text
manifest vacío

id inexistente

capabilities no es array

entryPoints.plugin inexistente
```

---

# 18. Validación runtime del id

Después de cargar `Plugin.qml`, se comprueba:

```qml
item.pluginId === manifest.id
```

Esto evita inconsistencias como:

```text
manifest:
id = network

Plugin.qml:
pluginId = netwrok
```

El plugin no se registra si ambos ids no coinciden.

# 28. Principio de diseño actual

El contrato actual sigue esta separación:

```text
manifest
→ metadata y capabilities

Plugin.qml
→ lifecycle y composición del plugin

Service.qml
→ lógica y estado funcional

BarWidget.qml
→ representación compacta

Panel.qml
→ superficie interactiva

PluginDiscovery
→ descubrir/cargar

PluginRegistry
→ registrar/consultar

Bar / PanelHost
→ montar capabilities
```

Cada capa tiene una responsabilidad específica.

---

# 29. Regla para próximos plugins

Un plugin no debe conocer directamente otras features globales salvo que sea estrictamente necesario.

Por ejemplo:

```text
Network BarWidget
NO conoce LauncherState
```

En su lugar:

```text
Network BarWidget
→ interacted()

Bar
→ decide cerrar Launcher
```

Esto reduce acoplamiento entre plugins y superficies globales.

# 31. Punto de retorno

Este checkpoint representa el primer estado donde TartarusShell dispone de una arquitectura de plugins funcional y probada con una feature real.

Si una migración futura rompe:

```text
PluginDiscovery
PluginRegistry
Bar capabilities
PanelHost
```

este estado puede usarse como referencia estable.

Siguiente paso natural:

```text
migrar Audio usando Network como implementación de referencia
```

sin rediseñar el sistema de plugins salvo que aparezca una necesidad realmente general.
