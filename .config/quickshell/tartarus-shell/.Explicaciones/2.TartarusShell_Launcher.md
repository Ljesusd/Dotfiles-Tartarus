# Checkpoint — TartarusShell: Launcher modularizado

**Estado:** funcional.

## Objetivo de este checkpoint

Separar responsabilidades dentro del launcher para evitar que `Launcher.qml` concentre toda la interfaz y toda la interacción.

El launcher ahora usa componentes dedicados para:

- búsqueda y teclado
- representación de aplicaciones
- datos y lógica de aplicaciones

## Estructura relevante

```text
TartarusShell/
├── shell.qml
├── launcher/
│   ├── Launcher.qml
│   ├── assets/
│   └── components/
│       ├── SearchBar.qml
│       └── AppItem.qml
└── services/
    └── Applications.qml
```

## Arquitectura actual del launcher

```text
Launcher.qml
│
├── Applications
│   ├── obtiene DesktopEntries
│   ├── filtra por query
│   ├── ordena por frecuencia

├── SearchBar

    └── ...
```

## `SearchBar.qml`

`SearchBar.qml` es un `TextInput` especializado.

Su responsabilidad es recibir entrada del usuario y emitir intención, sin conocer directamente el `ListView`, `Applications` ni la ventana del launcher.

Interfaz principal:

```qml
property alias query: root.text

signal escapePressed()
signal moveUp()
signal moveDown()
signal acceptPressed()
```

### Decisión de diseño

`SearchBar` no modifica directamente:

```qml
appList.currentIndex
launcherWindow.visible
applications.query
```

En su lugar emite señales.

Ejemplo:

```text
↓
    ↓
SearchBar
    ↓ moveDown()
Launcher
    ↓
appList.currentIndex++
```

Esto mantiene separado:

```text
entrada
    ↓
intención
    ↓
lógica del launcher
```

## Integración de `SearchBar`

En `Launcher.qml` se sustituyó el antiguo `TextInput` inline por:

```qml
SearchBar {
    id: search

    anchors {
        top: parent.top
        left: parent.left
        right: parent.right
        margins: 30
    }

    onQueryChanged: {
        applications.query = query
        appList.currentIndex = 0
    }

    onEscapePressed: {
        launcherWindow.closeLauncher()
    }

    onMoveDown: {
        if (appList.currentIndex < appList.count - 1)
            appList.currentIndex++
    }

    onMoveUp: {
        if (appList.currentIndex > 0)
            appList.currentIndex--
    }

    onAcceptPressed: {
        if (appList.currentIndex >= 0) {
            applications.launch(
                applications.applications.values[appList.currentIndex]
            )

            launcherWindow.closeLauncher()
        }
    }
}
```

## `AppItem.qml`

`AppItem.qml` representa visualmente una aplicación.

Su interfaz principal es:

```qml
required property var application
required property bool selected

signal activated()
signal hovered()
```

El componente conoce:

```text
application
selected
icono
nombre
hover
click
```

pero no conoce:

```text
modelData
index
appList.currentIndex
Applications
launcherWindow
```

## Decisión de diseño sobre `AppItem`

Se decidió mantener `AppItem.qml` desacoplado del `ListView`.

No se movieron dentro del componente conceptos como:

```qml
modelData
index
ListView.isCurrentItem
ListView.view.currentIndex
```

Estos pertenecen al contexto del `ListView` y permanecen en `Launcher.qml`.

El contrato queda:

```text
          application
          selected
              ↓
        ┌───────────┐
        │  AppItem  │
        └───────────┘
              ↓
          activated()
           hovered()
```

Esto permite que `AppItem` siga siendo una representación de una aplicación y no un delegate rígidamente acoplado a `ListView`.

## Integración de `AppItem`

El antiguo:

```qml
delegate: Rectangle {
    ...
}
```

fue sustituido por:

```qml
delegate: AppItem {
    application: modelData
    selected: ListView.isCurrentItem

    onHovered: {
        appList.currentIndex = index
    }

    onActivated: {
        applications.launch(application)
        launcherWindow.closeLauncher()
    }
}
```

## `Applications.qml`

El servicio se mantiene separado en:

```text
services/Applications.qml
```

Responsabilidades actuales:

```text
1. Obtener DesktopEntries.
2. Filtrar aplicaciones usando query.
3. Ordenar según frecuencia de uso.
4. Cargar app-usage.json.
5. Actualizar app-usage.json.
6. Ejecutar aplicaciones.
```

No se modificó durante esta refactorización porque su responsabilidad ya está claramente separada de la interfaz.

## Responsabilidades finales

```text
Applications.qml
    datos y lógica de aplicaciones

SearchBar.qml
    entrada de texto y teclado

AppItem.qml
    representación e interacción de una aplicación

Launcher.qml
    coordinación del launcher
```

## Estado arquitectónico

```text
                     Launcher
                        │
          ┌─────────────┼─────────────┐
          │             │             │
    Applications     SearchBar      ListView
                                      │
                                 AppItem × N
```

`Launcher.qml` se está convirtiendo en un coordinador en lugar de contener todos los detalles de implementación.

## Patrón utilizado

La arquitectura favorece:

```text
propiedades de entrada
        ↓
componente
        ↓
signals de salida
```

Ejemplo con `AppItem`:

```text
application + selected
        ↓
     AppItem
        ↓
activated / hovered
```

Ejemplo con `SearchBar`:

```text
texto / teclado
       ↓
   SearchBar
       ↓
moveUp / moveDown / accept / escape
```

Este patrón reduce acoplamiento y hace los componentes más fáciles de reutilizar y extender.
